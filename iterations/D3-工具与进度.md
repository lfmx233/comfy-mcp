
# D3 · 工具与进度（2026-11-19）

## 目标

来自 docs/PLAN.md §10 的验收标准，原文：

> 产出：`server.py` 6 个工具、`jobs.py`、`errors.py`、进度映射。
> 验收：fake 上跑通 `run → progress ≥ 3 次 → result`；四类错误都有码。

D1 只暴露了 `comfy_status`，D2 造好了「图怎么转、参数怎么白名单」，但没人调用它们。D3 要把这两块拼成 Agent 真正能用的六个工具，并且解决一个 Agent 场景特有的问题：**一次出图 10 秒到 5 分钟，模型不能干等**。

## 关键决定

1. **新增第 10 个错误码 `EXECUTION_FAILED`。** PLAN 原本 9 个码，`CUDA_OOM` 只覆盖显存，而真实失败里还有 `RuntimeError: mat1 and mat2 shapes cannot be multiplied` 这种「图接错了」的错。没有兜底码时它会被 SDK 包成 `UnexpectedToolError`，栈信息进不了结构化结果，Agent 什么也读不到。代价是错误表面变大，收益是「任何执行期失败都有一个 retryable=false 的确定出口」。
2. **每个工具都套 `@_guarded`。** 直接 `raise` 会被 SDK 吞成 `UnexpectedToolError: Error executing tool comfy_run` 并丢掉 `code`。装饰器用 `functools.wraps` 包一层，把 `_Fail`（预检失败）和普通异常统一翻成 5 字段信封，同时保证 SDK 仍能从原签名里看到 `ctx` 参数。
3. **先连 ws 再 `POST /prompt`。** 反过来的话，很快的任务（缓存命中时 0.5 秒）会在连接建立前就发完 `execution_start` 与 `executed`，进度与输出全丢。`event_stream()` 做成 asynccontextmanager，连接成功才 yield，就是为了强制这个顺序。
4. **进度取 `max(上次, 本次)` 并封顶 99。** ws 事件会乱序也会重发，回退的进度条比没有进度更让模型困惑（它会以为任务重启了）。100 只在 `execution_success` 之后给，否则「99.9%」会被当成完成。
5. **判定结果以 `/history` 为准，不以 ws 帧为准。** ws 是「尽力而为」的：可能丢帧、可能断线。`_pump` 结束只当「该去查结果了」的信号，`succeeded/failed` 由 `GET /history/<pid>` 的 `status.status_str` 决定，这样断线也能收敛到正确结论。

## 踩坑

1. **只处理 `progress` 帧，真机上进度是「0, 0, 0, 99」。**

   第一版 `Progress.feed` 只认 `executing` / `progress` / `executed`。假服务器按这三个发，测试全绿；真机跑起来采样却是：

   ```text
   samples: [0.0, 0.0, 0.0, 0.0, 99.0, 99.0, 99.0, 99.0]
   ```

   抓原始帧才看清：0.3.60 除了老的 `progress`，还会发 `progress_state`，`data.nodes` 是**全量**节点状态字典：

   ```json
   {"type": "progress_state", "data": {"nodes": {"6": {"value": 3, "max": 8,
     "state": "running", "node_id": "6", "display_node_id": "6", "real_node_id": "6"}}}}
   ```

   补上这个分支后，同一台机器同一条工作流变成 `50.0 → 62.5 → 65.6 → 68.8 → 71.9 → 75.0 → 87.5 → 99.0 → 100.0`。**假服务器永远不会告诉你这件事**，只能靠真机。抓下来的 25 帧存进 `tests/fixtures/ws_frames_real.json`，并加了一个测试：把 `progress` 帧全部删掉也要求出 ≥ 3 个中间值——防止以后又被「只会照假服务器写测试」的改法退化。

2. **`report_progress` 在没有请求上下文时抛异常。**

   `tests` 里直接 `await server.call_tool(...)` 时 SDK 的 `Context` 没有 `request_context`，`ctx.report_progress()` 抛 `ValueError: Context is not available outside of a request`。这条异常如果没被兜住，会把一个正常完成的任务变成失败。`_report()` 因此整段 try/except：进度上报是锦上添花，绝不能连累任务。

3. **未捕获异常变成 `UnexpectedToolError`。**

   根因是 SDK 只把 `ToolError` 当领域错误，其余一律包装。现象是 `code` 丢了、`hint` 没了，Agent 只能看到一句「Error executing tool comfy_run」。解法是 `@_guarded`；另一个坑是装饰器必须保留签名（`functools.wraps`），否则 SDK 的参数解析看不到 `ctx`，注入失效。

4. **`Progress` 的 `done` 集合会被非本 prompt 的节点污染。**

   `progress_state` 的 `data.nodes` 里可能出现不在当前 prompt 里的 node id（子图、display node）。直接 `done.add` 会让 `len(done) > total`，进度冲到 100 再被 99 封顶，看起来「一直 99」。修法是 `_feed_state` 里先 `known = set(self.node_ids)`，只认自己的节点。

5. **验证脚本自己写错了终止条件。**

   第一版脚本在 `executing` 帧 `node is None` 就 break。缓存命中的任务只有 8 帧，break 得太早，`tracker.percent` 停在 99，看起来像 bug——其实是我自己的验证逻辑比被测代码更粗。教训：**验收脚本要么复用生产代码路径（`_pump`），要么至少和它同一套终止条件**，否则验的是脚本不是产品。

6. **`ruff --fix` 的 UP041 会把 `asyncio.TimeoutError` 改成内建 `TimeoutError`。**

   Python 3.11 起两者是同一个对象，改完测试仍绿；但代码里同时有 `except TimeoutError` 与 `except asyncio.CancelledError` 时，读起来容易误以为 `wait_for` 会抛两种不同的东西。保留 ruff 的结果，因为它符合 3.11+ 的事实。

## 遗留

1. **`outputs[].width/height` 仍是 `null`。** `/history` 不返回尺寸；D4 取图做缩略时会读 PNG/JPEG 头，那时顺手补上。先留 null 而不是猜，是因为猜错会让「5 张图 20KB」的预算算错。
2. **`comfy_job` 只查内存表。** 重启后查不到，D4 的 `runs/<job_id>.json` 落盘与启动扫描补。
3. **manifest 里的 `models[].sha256` 是 `null`。** 要算哈希得把模型文件读一遍（本机 2–6GB），D4 用「按 mtime+size 缓存」的方式做，不能每次跑都读盘。
4. **多实例仍未真正启用。** `instances.yaml` 能配多条，工具也能选，但「按 tags/models 自动挑实例」留给 D5。
5. **`comfy_cancel` 没有真机验证。** 假服务器上验证了（取消后队列清空），真机上目前只验证了超时路径里的 `_abort`，两者走同一个函数。D5 补一条真机取消。
